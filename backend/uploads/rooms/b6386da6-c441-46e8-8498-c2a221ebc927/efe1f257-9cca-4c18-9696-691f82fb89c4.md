# Helpdesk / ITSM System — Full Design

Stack assumption: **Python (FastAPI)**, **DuckDB (in-memory)** for persistence, **in-process/RabbitMQ-swappable Event Bus**, **WebSocket** for live push, **React** frontend (matches your existing ITSM stack conventions).

Key design decision: **the Event Bus is the single source of truth for "what happened"**. Every state transition, lock action, message, escalation, reassignment, SLA breach, CSAT submission, login, user activation, etc. is emitted as an event and persisted to an append-only `events` table. REST endpoints for history are just queries over this table (or projections built from it); WebSocket is simply "tail -f" on the bus. This satisfies "kanban/timeline can be a module connected to the event bus instead of integrating into the system" — it's a separate consumer process subscribing to the same bus.

## 2. Roles & Technician Levels

```
Role enum:        EMPLOYEE, TECHNICIAN, ADMIN
Technician tier:   VIRTUAL, HUMAN        (only meaningful when role = TECHNICIAN)

Escalation chain:  VIRTUAL -> HUMAN -> ADMIN
Assignment order:  VIRTUAL (online) -> HUMAN (online) -> (queued, unassigned)
```

Virtual technicians are **not humans registering through the normal flow** — they are separate bot servers that connect via API using a **non-expiring token** (see §9 Auth). Everyone else (employee, human technician, admin) gets a normal expiring JWT.

## 4. Event Bus

```python
# event_bus.py
from abc import ABC, abstractmethod
import json, duckdb, datetime

class EventBus(ABC):
    @abstractmethod
    async def publish(self, event_type: str, payload: dict,
                       ticket_id: int | None = None, actor_id: int | None = None): ...

    @abstractmethod
    def subscribe(self, event_type: str | None, handler): ...
    # event_type=None means "subscribe to everything" (used by kanban/timeline/monitor modules)


class InProcessEventBus(EventBus):
    """Default. Swappable for RabbitMQEventBus without touching services."""
    def __init__(self, db_conn):
        self.db = db_conn
        self._subscribers: list[tuple[str | None, callable]] = []

    async def publish(self, event_type, payload, ticket_id=None, actor_id=None):
        row = self.db.execute(
            """INSERT INTO events (event_type, ticket_id, actor_id, payload)
               VALUES (?, ?, ?, ?) RETURNING id, created_at""",
            [event_type, ticket_id, actor_id, json.dumps(payload)]
        ).fetchone()
        event = {
            "id": row[0], "event_type": event_type, "ticket_id": ticket_id,
            "actor_id": actor_id, "payload": payload, "created_at": row[1].isoformat()
        }
        for etype, handler in self._subscribers:
            if etype is None or etype == event_type:
                await handler(event)
        return event

    def subscribe(self, event_type, handler):
        self._subscribers.append((event_type, handler))


class RabbitMQEventBus(EventBus):
    """Same publish() signature, backed by an exchange; used when other real
    external systems (not just internal WS modules) need to consume events,
    e.g. the Virtual Technician server, external ITSM integrations, etc."""
    ...
```

The **WebSocket broadcaster**, **Kanban projection**, and **Timeline projection** are all just `subscribe(None, handler)` consumers — they don't touch `TicketService` directly, satisfying "can be a module connected to the event bus instead of integrating into the system."

```

USER_PASSWORD_CHANGED, USER_PROFILE_UPDATED,

MESSAGE_SENT, MESSAGE_EDITED, MESSAGE_DELETED,

REASSIGN_REQUESTED, REASSIGN_APPROVED, REASSIGN_REJECTED,
```

## 5. Ticket State Machine

```
                 spam filter (stub=True)
NEW  ───────────────────────────────────► NEW (persisted)
 │
 │ AssignmentService picks technician (virtual first)
 ▼
IN_PROGRESS ──────────────► RESOLVED   (technician or admin resolves)
 │        │                 (terminal — cannot reopen; user must file new ticket)
 │        │
 │        └───────────────► REJECTED   (technician/admin marks not a real issue)
 │                            (terminal)
 │
 ├──(technician/virtual requests escalate)──► AWAIT_ESCALATE ──approved──► IN_PROGRESS (reassigned up a tier)
 │                                                          └──rejected──► IN_PROGRESS (unchanged)
 │
 ├──(technician requests reassign)──► AWAIT_REASSIGN ──approved──► IN_PROGRESS (new assignee)
 │                                                    └──rejected──► IN_PROGRESS (unchanged)
 │
 └──(no message update in 30 min, AND not RESOLVED/REJECTED)──► TIMEOUT (terminal)

SLA near-breach (independent of the above): auto-creates an escalation
directly into the admin queue (does NOT change ticket state by itself;
only an approved escalation/reassign or a resolve/reject/timeout changes state).
```

Rules:
- `RESOLVED`, `REJECTED`, `TIMEOUT` are **terminal** — no reopening. A brand-new ticket must be filed.
- `AWAIT_ESCALATE` / `AWAIT_REASSIGN` block ordinary technician actions on the ticket (chat can continue, but resolve/lock-based actions wait on admin) — implemented as a guard in `TicketService`, not a DB constraint.
- The 30-minute timeout is evaluated against `last_message_at`, updated on every `MESSAGE_SENT` event (any participant, including the assignee). A background scheduler (APScheduler or a simple asyncio loop) scans `tickets WHERE state IN ('NEW','IN_PROGRESS','AWAIT_ESCALATE','AWAIT_REASSIGN') AND last_message_at < now() - 30min` every minute and transitions them to `TIMEOUT`, emitting `TICKET_TIMEOUT`.

## 6. Priority / SLA Calculation

```python
# sla_service.py
class SLAService:
    def __init__(self, db):
        self.db = db

    def resolve_priority(self, urgency: str, impact: str) -> str:
        row = self.db.execute(
            "SELECT priority FROM priority_matrix WHERE urgency=? AND impact=?",
            [urgency, impact]
        ).fetchone()
        if not row:
            raise ValueError(f"No priority mapping for {urgency}/{impact}")
        return row[0]

    def compute_due_times(self, priority: str, created_at: datetime):
        policy = self.db.execute(
            "SELECT first_response_mins, resolve_mins FROM sla_policy WHERE priority=?",
            [priority]
        ).fetchone()
        frt, rt = policy
        return (
            created_at + timedelta(minutes=frt),
            created_at + timedelta(minutes=rt),
        )
```

Example seed data (tune to your org):

| Urgency \ Impact | LOW | MEDIUM | HIGH | CRITICAL |
|---|---|---|---|---|
| LOW | P4 | P4 | P3 | P2 |
| MEDIUM | P4 | P3 | P2 | P1 |
| HIGH | P3 | P2 | P1 | P1 |
| CRITICAL | P2 | P1 | P1 | P1 |

| Priority | First response | Resolve | Near-breach % |
|---|---|---|---|
| P1 | 15 min | 4 hours | 80% |
| P2 | 30 min | 8 hours | 80% |
| P3 | 2 hours | 24 hours | 80% |

## 7. Assignment Algorithm

```python
# assignment_service.py
class AssignmentService:
    def __init__(self, db, event_bus):
        self.db, self.event_bus = db, event_bus

    async def assign(self, ticket_id: int):
        # 1. Try an online VIRTUAL technician (round-robin / least-loaded)
        candidate = self.db.execute("""
            SELECT id FROM users
            WHERE role='TECHNICIAN' AND tech_tier='VIRTUAL'
              AND status='ACTIVE' AND online_status='ONLINE'
            ORDER BY (SELECT count(*) FROM tickets t
                      WHERE t.assigned_to = users.id AND t.state='IN_PROGRESS')
            LIMIT 1
        """).fetchone()
        tier = 'VIRTUAL'

        # 2. Fall back to online HUMAN technician
        if not candidate:
            candidate = self.db.execute("""
                SELECT id FROM users
                WHERE role='TECHNICIAN' AND tech_tier='HUMAN'
                  AND status='ACTIVE' AND online_status='ONLINE'
                ORDER BY (SELECT count(*) FROM tickets t
                          WHERE t.assigned_to = users.id AND t.state='IN_PROGRESS')
                LIMIT 1
            """).fetchone()
            tier = 'HUMAN'

        if not candidate:
            # 3. Nobody online -> stays NEW / unassigned, retried by a periodic
            #    "unassigned ticket sweep" job every N seconds until someone comes online.
            return None

        assignee_id = candidate[0]
        self.db.execute(
            "UPDATE tickets SET assigned_to=?, assigned_tier=?, state='IN_PROGRESS', updated_at=now() WHERE id=?",
            [assignee_id, tier, ticket_id]
        )
        self.db.execute("""
            INSERT INTO ticket_participants (ticket_id, user_id, tier)
            VALUES (?, ?, ?)
            ON CONFLICT (ticket_id, user_id) DO UPDATE SET last_at=now()
        """, [ticket_id, assignee_id, tier])

        await self.event_bus.publish("TICKET_ASSIGNED",
            {"assignee_id": assignee_id, "tier": tier}, ticket_id=ticket_id)
        await self.event_bus.publish("TICKET_STATE_CHANGED",
            {"from": "NEW", "to": "IN_PROGRESS"}, ticket_id=ticket_id)
        return assignee_id
```

- "Least-loaded" tie-break shown above; swap for pure round-robin if preferred.
- A lightweight **unassigned sweep** background task re-runs `assign()` for any ticket still `NEW`/unassigned whenever a `USER_ONLINE` event fires for a technician, and on an interval as a safety net.

## 8. Escalation & Reassignment Flow

```python
# escalation_service.py
LEVEL_RANK = {"VIRTUAL": 0, "HUMAN": 1, "ADMIN": 2}

class EscalationService:
    async def request_escalation(self, ticket_id, requester_id, reason):
        requester_tier = self._tier_of(requester_id)          # VIRTUAL or HUMAN
        to_tier = "HUMAN" if requester_tier == "VIRTUAL" else "ADMIN"

        self.db.execute("""INSERT INTO escalation_requests
            (ticket_id, requested_by, from_tier, to_tier, reason)
            VALUES (?,?,?,?,?)""", [ticket_id, requester_id, requester_tier, to_tier, reason])
        self.db.execute("UPDATE tickets SET state='AWAIT_ESCALATE', updated_at=now() WHERE id=?", [ticket_id])
        await self.event_bus.publish("ESCALATION_REQUESTED",
            {"requested_by": requester_id, "from_tier": requester_tier, "to_tier": to_tier, "reason": reason},
            ticket_id=ticket_id)
        # lands in admin queue automatically because admin queue = query over
        # escalation_requests WHERE status='PENDING' (+ reassign_requests, + SLA near-breach flags)

    async def resolve_escalation(self, escalation_id, admin_id, approve: bool, new_assignee_id=None):
        req = self._get(escalation_id)
        status = "APPROVED" if approve else "REJECTED"
        self.db.execute("UPDATE escalation_requests SET status=?, resolved_by=?, resolved_at=now() WHERE id=?",
                         [status, admin_id, escalation_id])
        if approve:
            target = new_assignee_id or self._pick_next_tier_assignee(req["to_tier"])
            self.db.execute("""UPDATE tickets SET assigned_to=?, assigned_tier=?, state='IN_PROGRESS',
                                updated_at=now() WHERE id=?""", [target, req["to_tier"], req["ticket_id"]])
            await self.event_bus.publish("ESCALATION_APPROVED", {...}, ticket_id=req["ticket_id"])
        else:
            self.db.execute("UPDATE tickets SET state='IN_PROGRESS', updated_at=now() WHERE id=?", [req["ticket_id"]])
            await self.event_bus.publish("ESCALATION_REJECTED", {...}, ticket_id=req["ticket_id"])
```

`reassign_requests` mirrors the same shape, minus tier logic — it just proposes/approves a different assignee at the **same** tier, and admin resolves it directly from the same queue.

**Admin queue** = a single view combining:
```sql
SELECT 'ESCALATION' AS kind, * FROM escalation_requests WHERE status='PENDING'
UNION ALL
SELECT 'REASSIGN' AS kind, * FROM reassign_requests WHERE status='PENDING'
UNION ALL
SELECT 'SLA_NEAR_BREACH' AS kind, * FROM <derived near-breach rows>
```
Admin can act on any row directly: approve/reject escalation or reassign, or — per spec — **resolve the underlying ticket right away** without going through the technician (`PATCH /admin/tickets/{id}/resolve`), or reassign to a specific technician (`PATCH /admin/tickets/{id}/reassign`).

## 9. Locking

```python
# lock_service.py — in-memory only
class LockService:
    def __init__(self, event_bus):
        self._locks: dict[int, dict] = {}
        self.event_bus = event_bus

    async def toggle_acquire(self, ticket_id: int, user_id: int) -> bool:
        """Technician clicks a toggle (not automatic) before acting on a message."""
        current = self._locks.get(ticket_id)
        if current and current["holder_id"] != user_id:
            return False  # someone else holds it
        if current and current["holder_id"] == user_id:
            del self._locks[ticket_id]
            await self.event_bus.publish("TICKET_LOCK_RELEASED", {"user_id": user_id}, ticket_id=ticket_id)
            return True
        self._locks[ticket_id] = {"holder_id": user_id, "acquired_at": datetime.utcnow()}
        await self.event_bus.publish("TICKET_LOCK_ACQUIRED", {"user_id": user_id}, ticket_id=ticket_id)
        return True

    def is_locked_by_other(self, ticket_id: int, user_id: int) -> bool:
        current = self._locks.get(ticket_id)
        return bool(current and current["holder_id"] != user_id)

    async def force_release(self, ticket_id: int, admin_id: int):
        self._locks.pop(ticket_id, None)
        await self.event_bus.publish("TICKET_LOCK_FORCE_RELEASED", {"admin_id": admin_id}, ticket_id=ticket_id)
```

All mutating ticket endpoints (resolve, reject, escalate, reassign, send-as-technician) check `is_locked_by_other()` and return `409 Locked` if held by someone else. Admin's `force_release` bypasses this for anyone.

## 10. Auth

- Standard username/password + JWT for `EMPLOYEE`, `TECHNICIAN(HUMAN)`, `ADMIN` — short-lived access token + refresh token, normal expiry.
- Virtual technicians authenticate via a **separate token type** (`token_type: "virtual_service"`) issued once at registration/approval by an admin, with **no expiry** (`exp` omitted or far future), scoped only to the virtual-technician API surface (`/tickets/{id}/messages`, `/tickets/{id}/resolve`, `/escalations`, `/tickets/mine`, presence heartbeat). Store the raw token hashed, same as a password, revoke by deleting the row instead of relying on expiry.
- New registrations (`EMPLOYEE` or `TECHNICIAN`) default to `status='PENDING'` and cannot log in (or log in but get a read-only "awaiting activation" state) until an admin flips them to `ACTIVE` via `/admin/users/{id}/activate`.


All WS endpoints are thin: on connect, send a snapshot (via the same service the REST GET would use), then `event_bus.subscribe(...)` and forward matching events as JSON frames. On disconnect, unsubscribe (and for `/ws/tickets/{id}` from a technician/employee, optionally flip `online_status` if that was their last connection).

```python
@router.websocket("/ws/admin/timeline")
async def ws_timeline(ws: WebSocket, ticket_id: int | None = None):
    await ws.accept()
    await ws.send_json(history_service.get_recent_events(ticket_id))  # snapshot via REST-equivalent query
    queue = asyncio.Queue()
    def handler(event):
        if ticket_id is None or event["ticket_id"] == ticket_id:
            queue.put_nowait(event)
    event_bus.subscribe(None, handler)
    try:
        while True:
            event = await queue.get()
            await ws.send_json(event)
    except WebSocketDisconnect:
        pass
```

## 15. Timeout & Terminal-State Enforcement

- Background job (`asyncio` task or APScheduler `IntervalTrigger(seconds=60)`):
  ```python
  async def timeout_sweep(db, event_bus):
      rows = db.execute("""
          SELECT id FROM tickets
          WHERE state IN ('NEW','IN_PROGRESS','AWAIT_ESCALATE','AWAIT_REASSIGN')
            AND last_message_at < now() - INTERVAL 30 MINUTE
      """).fetchall()
      for (ticket_id,) in rows:
          db.execute("UPDATE tickets SET state='TIMEOUT', updated_at=now() WHERE id=?", [ticket_id])
          await event_bus.publish("TICKET_TIMEOUT", {}, ticket_id=ticket_id)
  ```
- All write endpoints (`/messages`, `/resolve`, `/reject`, `/escalate`, `/reassign-request`) reject with `409` if `ticket.state IN ('RESOLVED','REJECTED','TIMEOUT')`.
- Frontend: employee's `/tickets/:id` shows a persistent banner "This ticket is closed — create a new ticket to continue" with a CTA to `/tickets/new`, no reopen affordance anywhere in the UI.

## 16. CSAT Flow

1. On `TICKET_RESOLVED` (or `/admin/tickets/{id}/resolve`), the resolve handler queries `ticket_participants` for that ticket, filters to `tier='HUMAN'`, and inserts a `csat_surveys` row per distinct human technician (score left NULL = pending).
2. `GET /tickets/{id}/csat` (employee) returns those pending rows.
3. `POST /tickets/{id}/csat/{technician_id}` fills in score/comment, emits `CSAT_SUBMITTED`.
4. Virtual technicians are simply never inserted into `csat_surveys` (filtered out by tier at step 1) — no special-case branching needed elsewhere.
